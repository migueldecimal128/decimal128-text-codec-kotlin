# decimal128-text-codec-kotlin

Thin codec between the two IEEE 754-2019 decimal128 interchange encodings — BID
and DPD — and decimal character sequences, for Kotlin Multiplatform.

Derived from `decimal128-kotlin-legacy/decimal128-bid-string-codec`, which was
BID-only; the DPD back end was built alongside it. One file, one `object`, no
runtime dependencies.

## API

```kotlin
import com.decimal128.textcodec.Decimal128TextCodec

// bits -> text
val s: String = Decimal128TextCodec.bid128ToString(hi, lo)
val d: String = Decimal128TextCodec.dpd128ToString(hi, lo)

// text -> bits; returns null on success, an error message on failure
val bits = LongArray(2)
val err: String? = Decimal128TextCodec.bid128Parse(bits, "1.23E+45")
val errD: String? = Decimal128TextCodec.dpd128Parse(bits, "1.23E+45")
```

Values are a pair of `Long`s: index 0 is the high 64 bits of the encoding,
index 1 the low 64. Both parse functions always write `out` — the canonical
positive quiet NaN on failure — so a caller who ignores the return value still
observes a legal IEEE 754-2019 datum.

## Scope

Rounding, where required, is `roundTiesToEven` and is not configurable. Output
is the GDAS `to-scientific-string` form and is not configurable — the exponent
sign is always written (`6.02E+23`), and cohort information is preserved. No
arithmetic, no field extraction, no value-type wrapper.

Accepted input matches what the full `decimal128-{lang}` ports accept. That
includes the parenthesised NaN payload: **`NaN(123)` as well as `NaN123`**,
matching the spelling C's `strtod` reads. The form is positional and balanced —
`(` immediately after the word, at least one digit, `)` last — so `NaN()`,
`NaN(1`, `NaN(1)2(3)`, `NaN[1]` and `NaN{1}` are all rejected. Rendering never
emits parentheses. The codecs had this before the ports did; the ports took it
on 2026-08-23, closing the family's one grammar divergence.

For the full decimal128 implementation see `decimal128-kotlin` at
<https://decimal128.com>.

## Targets

jvm, macosArm64, macosX64, linuxX64, iosArm64, iosSimulatorArm64, js(node).

## Tests

```
git submodule update --init --recursive
./gradlew jvmTest macosArm64Test jsNodeTest
```

Two test classes in one file, plus the `actual`s for the one KMP seam.
The canonical table is its own class but shares a file with the other tables, so
the two table runners they both use stay private to it — the same layout the C,
Swift, Java and C# ports use.

| file | what it covers |
|---|---|
| `commonTest/.../TestCorpusVectors.kt` | `TestCorpusVectors` — the four conformance tables over the shared corpus, 2,601 rows, both directions, both formats. Also holds the corpus reader, the hex helpers and the `expect` loader, all of which it is the only consumer of. |
| | `TestCanonicalCorpus` — the full 84,783-row canonical table |
| `{jvm,native,js}Test/.../XPlatformLoadTestResource*.kt` | the loader's three `actual`s — `java.io.File`, POSIX `fopen`/`fread`, and Node `fs`. Three APIs in three source sets, which is the whole reason `expect`/`actual` exists; they are the only test files this port has that the others do not. |

That is the whole suite, and the shape is deliberate: **every test vector in this
repo comes from the shared corpus.** There is no hand-written table left, and
nothing reaches past the four public functions.

An exhaustive unit test of the DPD declet primitives used to sit here too. It was
removed once instrumentation showed the corpus already drives all 1024 declet
patterns through the decoder and all 1000 values through the encoder -- the
canonical table supplying the 1000 by sheer volume, and the noncanonical table's
462 declet rows supplying the 24 patterns a canonical encoder never emits. What
went with it is the *statement* that there are exactly 24: the corpus proves each
one decodes correctly without asserting how many there are.

The repo is standalone: it depends on no decimal128 port, at runtime or in
tests. The independent oracle is the shared `text_bid_dpd` corpus, generated by
the decimal128-c engine, which reaches its answers by different algorithms than
this codec does.

Hand-written vector tables used to sit alongside the corpus here -- BID render,
round-trip and parse tables, DPD render and parse tables, and the Cowlishaw
`dqEncode` / `dqCanonical` suite, along with the contract tests that rode with
them. They are gone. Every input they held that the corpus did not
is now a corpus row, engine-authored, and the Cowlishaw files themselves live in
`decimal128-resources` under `rosetta/dectest`, so nothing is beyond a reader's
reach. Those tables were transcribed by hand into three languages at once, which
is what made them worth removing: a whole vector shape -- `apply #a -> #b` -- had
silently fallen out of all three copies, and no test could have told us.

The vectors are read from `resources/text_bid_dpd`, where `resources` is the
`decimal128-resources` submodule -- the same mount every decimal128 port uses.
Nothing is copied into this repo, so there is no drift class to police. Because
`commonTest` has no portable file access, reaching a data file needs one KMP
seam, `loadTestResourceAsString`, with an actual per platform family: the JVM and
native read the filesystem, Node reads through `fs`. The build hands each test
task the absolute corpus root in `DECIMAL128_RESOURCES`, so no runner's working
directory matters -- including the iOS simulator's sandbox, which gets it through
simctl's `SIMCTL_CHILD_` forwarding.
